1. How a CodeGym environment works

CodeGym (ByteDance Seed, arXiv 2509.17325) converts a static coding problem into an interactive, verifiable tool-use environment. An LLM wrote each environment as a small Gym-style Python class: the problem's atomic operations become named tools, the class keeps hidden state, and a Done(answer) tool checks the submitted answer against the oracle. We use the public HF release VanishD/CodeGym (envs_en: 23.5K environments; task_en_instruction_en_env: 80.1K task instances; each instance = environment + a JSON task configuration).

One episode, in order:

StepThe policy emits one function call. The environment's step(action_str) parses it, mutates hidden state, and returns an observation string.Each rollout gets its own spawned sandbox process running the env code (10 s step timeout); observations come back as user turns.
Terminationfinished() turns true after Done; the oracle solution ran solve_fc_round calls (train mean 28, eval 40–90).Budget H = 100 LLM calls; 10 consecutive turns without a call, a context overflow, or an env error end the episode as overlong.

The official server (github.com/StigLidu/CodeGym, online_server/) pins Python 3.11.2 and exposes the same three methods (step, finished, reward) over HTTP. We run the same env code in-process instead of through that server; the venv is Python 3.12.12, which matters in section 5.

Question

In an m×n grid, a robot is located at the top-left corner (marked as 'S') and needs to move to the bottom-right corner (marked as 'E'). The robot can only move right or down. Some cells in the grid are blocked (marked as '#') and the robot cannot pass through these cells, while open cells are marked as '.'. Your task is to determine the number of unique paths for the robot to go from 'S' to 'E' without passing through any blocked cells. For example, for the following 3×3 grid:
```
...
.#.
..E
```
There are 2 unique paths for the robot to move from the top-left corner to the bottom-right corner, so return 2.

The user turn also carries the standard rules block (same in every task):

Please answer the following question step by step according to the requirements below!

1. **Do not** write code to answer the user's question — you may only call the provided functions, and you may call at most **one function per step**.
2. After you call a function, wait for the tool to return the result — do not assume what the result will be.
3. If the tool’s description is unclear, you can try using it first, and then adjust your function call based on the returned result.
4. Function calls should be wrapped with `<|FunctionCallBegin|>....<|FunctionCallEnd|>` and contain a JSON-formatted list. The list should include **one dictionary**, where each dictionary contains two parameters:

   * `name`: the function name

Here’s an example of a function call:
<|FunctionCallBegin|>[{"name":"function_name", "parameters":{"key1":"value1", "key2":"value2"}}]<|FunctionCallEnd|>

**Extra requirements:**

* Do not overthink; think briefly, then decide how to call the function.
* Since you have many chances to call functions, you do not need to plan all steps in advance.
* Do not try to solve the problem without using the tools.

5. The degenerate trajectory

"Degenerate" is our word for a rollout that could not even start: the environment process failed before the first LLM call. The trainer still needs one row per rollout, so the loop emits a placeholder. Exactly one of the 9,452 environments in our split triggers this. Its code compiles on Python 3.11 (the official server's version) and not on 3.12:

line 189:  return f"First column does not need filling, current state: [{self.dp[i][0] for i in range(self.n)}]"

python3.11 -> parses OK
python3.12 -> SyntaxError: f-string: expecting '=', or '!', or ':', or '}'

An unparenthesised generator expression inside an f-string replacement field was tolerated by the old f-string tokenizer and is rejected by the PEG-based f-string grammar that Python 3.12 introduced (PEP 701). It is a Python-version incompatibility of one LLM-generated environment, not a runtime bug; the dataset card and the CodeGym repository do not mention it. The official fix is to run on 3.11; ours is to make the trainer robust to it.

This is the row our loop produces for that task (generated on the devbox with a scripted policy; the policy is never called):

RuntimeError: env start failed for Codeforces_5537_I__MinPathCostEnv: SyntaxError: f-string: expecting '=', or '!', or ':', or '}' (<codegym:MinPathCostEnv>, line 189)

DEGENERATE ROLLOUT OUTPUT: 1 row

Effect on training: the row is masked out and, because all 8 rollouts of that prompt get reward 0, its group advantage is zero, so the seed contributes nothing. The earlier crash happened because the placeholder lacked response_logprobs, which verl's rollout-vs-actor log-prob metric requires from every row.

The absolute numbers are not comparable, for four reasons in decreasing importance:

ReasonDetail
Policy modelQwen3.5-9B (2026, tool-use post-trained, hybrid attention) versus Qwen2.5-32B-Instruct (2024). The step-0 gap alone is 45 points on the 32K arm; the base model already solves most of these tasks.
Evaluation setThe paper's 128-problem held-out list was never released. Ours is a deterministic reconstruction from the public data (128 distinct unseen seeds whose oracle needs 40–90 calls, prompts ≤ 1,536 tokens). Same construction rule, different problems.
Prompt-length filterDropping tasks with prompts above 1,536 tokens (needed for the 4K arm) removes the longest tool lists, which skews both arms slightly easier.
Noise128 greedy samples give ±4 points at one standard error; consecutive validations moved by up to 10 points in both directions.

The comparison that survives all of this is the relative one the paper makes: SUPO at a 4K working context closing on GRPO at 32K. At step 40 the gap is 8 points (was 13 at step 0) with SUPO using 25% fewer tool calls and overrunning 5× less often.
